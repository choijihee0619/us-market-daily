# 세션 누락 감지·복구 설계

스케줄 실행이 조용히 빠졌을 때 그걸 알아채고 메우는 장치의 설계 문서다.
구현은 아직 없다. 이 문서는 **무엇을 왜 그렇게 만들 것인가**만 정한다.

작성 계기: 2026-08-06 세션이 통째로 누락됐고, 다음날 사람이 눈으로 발견했다.

---

## 1. 실패 양상 (관측 2건)

| 세션 | 원인 | 계층 | 발견 경로 |
|---|---|---|---|
| 2026-08-03 (월) | cron 요일을 `2-6`(화~토)로 지정 | 우리 코드 | 사람이 며칠 뒤 발견 |
| 2026-08-06 (목) | GitHub이 스케줄 이벤트를 발사하지 않음 | 외부 인프라 | 사람이 다음날 발견 |

두 원인은 다르지만 **증상이 같다. 누락이 실패로 보고되지 않는다.**

- 실패한 런이 있는 게 아니라 **런 자체가 없다.** `gh run list`에 이벤트가 0건이고,
  워크플로는 `active`이고, 빨간 X도 뜨지 않는다.
- 2026-08-06 건은 두 슬롯(20:50 / 22:20 UTC)이 동시에 빠졌다. 슬롯을 두 개 잡아둔
  이중화가 이 실패 유형에는 듣지 않는다는 뜻이다 — 서머타임과 러너 지연에는 듣지만,
  스케줄러가 그날 그 워크플로를 건너뛰면 둘 다 함께 사라진다.

### 왜 구멍이 영구적인가

`calendar_utils.last_completed_session()`은 **가장 최근 거래일 하나만** 돌려준다
(`src/calendar_utils.py` 의 역순 루프가 첫 매치에서 `return`한다).
그래서 놓친 날을 다시 방문하는 경로가 코드에 존재하지 않는다.
다음날 실행은 다음날 세션만 처리하고, 어제 구멍은 그대로 남는다.

`storage.upsert`가 멱등이라 **소급 실행은 안전하다.** 문제는 안전성이 아니라
아무도 소급 실행을 촉발하지 않는다는 것이다.

---

## 2. 설계상의 근본 제약

**같은 스케줄러 위에 올린 감지기는 같은 실패 양상을 공유한다.**

"세션이 뒤처졌는지 확인하는 워크플로"를 GitHub Actions cron으로 하나 더 잡는 건
직관적이지만 틀린 답이다. 그 감지기도 드롭될 수 있고, 드롭되면 **감지기가 조용해진
것과 정상인 것이 구분되지 않는다.** 침묵이 정상 신호인 시스템은 감지기가 아니라
위안이다. 이 프로젝트가 이미 배운 교훈("경고 없음은 정상의 증거가 아니다")이
스케줄러 층위에서 그대로 반복된다.

그래서 감지는 **부재를 트리거로 삼는 외부 장치**여야 하고,
손실 방지는 **감지와 별도로** 파이프라인 자체가 해야 한다.

---

## 3. 4개 계층

### 계층 1 — 갭 자동 메움 (예방)

손실을 실제로 막는 건 이것뿐이다. 감지는 사람이 움직여야 복구되지만,
이건 다음 실행이 알아서 메운다. 08-03과 08-06 둘 다 자동으로 복구됐을 것이다.

- `calendar_utils`에 `missing_sessions(data_dir, lookback) -> list[Timestamp]` 추가.
  `trading_days()`와 `residuals.parquet`에 실재하는 세션 집합을 차집합한다.
  잔차를 기준으로 삼는 이유: 가격만 있고 잔차가 없는 세션은 반쪽이므로 채워야 한다.
- `run_daily.py`에 `--fill-gaps N` 추가. 매 실행이 **가장 오래된 누락부터** N개를
  먼저 처리하고 그 다음 당일을 처리한다.

**예산이 구속 조건이다.** AV 무료 티어 25요청/일이고 세션당 7회를 쓴다
(토픽 배치 7개, 2장 참조). 당일 몫 7회를 남겨야 하므로 `N ≤ 2` (7×3=21 ≤ 25).
이 상한을 코드에 박아두지 않으면 갭 메움이 당일 뉴스 수집을 조용히 굶긴다 —
**4장에 적힌 무증상 실패를 새로 하나 만드는 셈이다.** 상한 초과 시 경고를 남기고
남은 갭은 다음 실행으로 넘긴다.

**오래된 갭은 자동으로 메우지 않는다.** 기본 상한을 5세션으로 두고 그보다 오래된
구멍은 목록만 보고한다. 근거는 4절.

**갭 메움은 블로그 산출물을 만들지 않는다.** 4일 지난 글을 발행할 일은 없고,
갭을 메우는 목적은 연구 기록(잔차·신호·채점)의 연속성이다. 차트·서술·붙여넣기
패키지를 건너뛰면 OpenAI 호출도 절약된다. 기존 `--backfill`은 수집만 하고
잔차·채점까지 건너뛰므로 그대로는 못 쓴다. 새 모드가 필요하다.

### 계층 2 — 소급 실행 표시 (연구 무결성)

**계층 1보다 먼저 들어가야 한다.** 순서가 뒤집히면 첫 자동 메움이 표시 없이
기록에 섞이고, 그 뒤로는 어느 행이 실시간이었는지 복원할 방법이 없다.

- `signals`·`scorecard`에 `run_at`(UTC 실행시각)과 `lag_sessions`(세션과 실행 사이
  거래일 수, 실시간이면 0) 추가.

**왜 필요한가.** 이 프로젝트의 자산은 "실시간 out-of-sample 기록"이다(1장).
소급 실행된 세션은 그것과 같지 않다. 2026-08-06 복구에서 직접 관측했다 —
하루 늦게 부른 AV가 **1,253건**을 돌려줬고, 2026-07-30 실시간 실측은 1,058건이었다.
소급 수집이 더 많은 기사를 준다. 데이터가 더 좋아졌는지 나빠졌는지는 논점이 아니다.
**실시간 실행이 볼 수 있었던 정보집합과 다르다**는 게 논점이고, 표시 없이 섞으면
out-of-sample 주장이 조용히 무너진다.

7장 2단계 항목 11~13(Fama-MacBeth, event study, 토픽 회귀 유의성)은 이 플래그로
표본을 갈라야 한다. 최소한 `lag_sessions > 0` 행을 제외한 robustness check를 병행한다.

git 커밋 날짜로 사후 복원하는 건 대안이 못 된다. rebase·amend에 취약하고
parquet에서 질의할 수 없다.

### 계층 3 — 외부 dead-man's switch (감지)

2절의 제약을 통과하는 유일한 감지기다. **침묵이 알람을 만든다.**

- 워크플로 마지막에 성공 시에만 외부 URL을 핑한다.
  `if: success()` + `curl -fsS -m 10 --retry 3 "$HEALTHCHECK_URL"`, 시크릿으로 주입.
- 외부 서비스가 유예시간 안에 핑을 못 받으면 메일·웹훅으로 알린다.
  GitHub 스케줄러에 의존하지 않으므로 스케줄 드롭을 감지할 수 있다.
- 유예시간은 넉넉해야 한다. 실측 러너 지연이 +53~68분이라 1차 실행이 실제로는
  21:40~22:00 UTC에 끝난다(7장 워크플로 주석). **3시간 이상**을 권한다.
  짧게 잡으면 거짓 알람이 쌓이고, 거짓 알람은 계층 4의 오탐과 같은 방식으로
  경고 신호를 마비시킨다.
- 하루 두 슬롯이 돌지만 핑은 하루 1건 이상이면 정상으로 봐야 한다
  (2차는 변경 없으면 커밋을 건너뛴다).
- 무료 티어로 되는 서비스가 있다(healthchecks.io 등). 구체 선택과 한도는
  `[검증 필요]`. 외부로 나가는 정보는 "런이 성공했다"는 사실뿐이고 데이터는 없다.

### 계층 4 — 로컬 신선도 확인 (사람 루틴 편승)

가장 싸고 가장 먼저 만들 것. 운영자가 매일 5분 붙여넣기 루틴을 이미 돌리므로
거기에 0단계로 끼우면 추가 비용이 거의 없다. 이것만으로도 08-06을 하루 안에 잡는다.

- `scripts/check_freshness.py`: `last_completed_session()`과 `residuals.parquet`의
  최대 세션을 비교한다. 뒤처져 있으면 누락 목록과 복구 명령을 찍고 종료코드 1.
- **`out/*/tistory/README.txt`에 실으면 안 된다.** 그 파일은 실행이 있었을 때만
  생기므로, 실행이 없는 바로 그 상황에서 아무 말도 하지 않는다. 독립 실행이어야 한다.

---

## 4. 하지 않을 것

- **감지용 GitHub Actions cron 추가.** 2절. 같은 실패 양상을 공유하면서
  감시하고 있다는 착각만 준다.
- **오래된 갭을 자동으로 메우기.** AV 뉴스 색인은 시간이 지나면 이동한다
  (기사 추가·삭제, 점수 재계산). 몇 주 지난 세션을 지금 부르면 그날 실시간
  실행이 볼 수 있었던 것과 상당히 다른 집합이 온다. 하루 늦은 복구는 실측으로
  괜찮았지만 그 결과를 몇 주로 외삽할 근거가 없다 `[검증 필요 — 표본 1건]`.
  오래된 갭은 사람이 의식적으로 결정할 일이고, 조용한 따라잡기로 처리하면 안 된다.
- **2026-08-03 세션을 이 작업에 끼워 복구하기.** 4세션 지난 건이라 위 항목에
  해당한다. 계층 2가 먼저 들어가 lag가 기록된 뒤에 별건으로 판단한다.

---

## 5. 구현 순서

순서에 의미가 있다. **2번이 3번보다 먼저다** — 표시 없는 자동 메움은
기록을 오염시키고 되돌릴 수 없다.

| 순 | 계층 | 항목 | 효과 |
|---|---|---|---|
| 1 | 4 | `check_freshness.py` | 의존성 없이 하루 안에 감지 |
| 2 | 2 | `run_at` · `lag_sessions` 스탬프 | 소급 실행을 연구에서 분리 가능 |
| 3 | 1 | `missing_sessions()` + `--fill-gaps` | 손실 자동 복구 |
| 4 | 3 | dead-man's switch 핑 | 사람 없이도 감지 |

1번만 해도 이번 사건은 잡힌다. 3번까지 가면 사람이 개입하지 않아도 기록이 이어진다.
4번은 외부 서비스 가입이 필요해 마지막이다.

---

## 6. 남는 한계

`storage.upsert`가 멱등이고 계층 1이 갭을 메워도, **한 번 지나간 실시간성은
복원되지 않는다.** 계층 2가 하는 일은 그 사실을 지우지 않고 기록에 남기는 것뿐이다.
채점(4번 블록)의 out-of-sample 성격을 엄격히 보려면 `lag_sessions = 0` 행만 써야 하고,
그러면 표본이 줄어든다. 이건 해결되는 문제가 아니라 감수하고 보고할 문제다.
